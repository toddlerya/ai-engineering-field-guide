# 选择作品集项目

请从真实的行业领域和具体的企业痛点出发，而不是从你想要尝试的某种炫酷技术出发。

**推荐选择工作流**：

1. 筛选出 5 个候选行业领域
2. 锁定 1 个目标领域
3. 在该领域中挑选具体企业
4. 深度分析这些企业的招聘启事与技术博客
5. 提取出具体的业务痛点
6. 设计大约 5 个候选项目创意
7. 为每个候选项目做技术选型

遵循这一顺序至关重要，因为“技术优先”的项目往往会变成生硬堆砌时髦词汇的 Demo，缺乏真正的实用价值。


## 1. 筛选 5 个候选行业领域

首先挑选 5 个备选行业。

根据本指南的 [应用案例分析](../role/04-use-cases_zh.md)，招聘中最常出现的行业领域包括：
- 金融 (finance) —— 2,321 次提及
- 医疗健康 (healthcare) —— 1,783 次提及
- 法律与合规 (legal / regulatory) —— 1,094 次提及
- 网络安全 (cybersecurity) —— 1,028 次提及
- 在线教育 (education) —— 571 次提及

这并不是全部可选行业，但它们是基于本仓库真实招聘数据总结出的、极具实操价值的备选池。

其他值得考虑的行业领域：
- 开发者工具 (developer tools)
- 智能客服 (customer support)
- 工业制造与供应链 (manufacturing and industrial)
- 零售与电商 (retail and e-commerce)
- 物流与仓储 (logistics)


## 2. 锁定 1 个目标领域

从上述 5 个候选行业中挑选 1 个深耕。

请使用以下 3 条标准进行校验筛选：
- 确认该行业领域有大量公司正在招聘 AI 工程师。
- 确认这些公司公开了你可以钻研和参考的技术博客、文档、招聘启事或 Demo。
- 确认你可以通过公开数据集或合成数据构建出符合该行业真实情况的模拟项目。

如果你实在纠结，可以先挑一个你非常想去的公司，然后直接采用该公司所在的行业领域。


## 3. 在目标领域中挑选具体公司

在选定领域内挑选 5 到 10 家公司。

搜集关于这些公司的以下资料：
- 当前正在开放的职位招聘描述 (Job Descriptions)
- 公司的官方技术博客
- 阐述了具体业务流程的产品文档
- 公开的系统 Demo 或客户支持 FAQ 文档
- 可以获得的公开数据集或样板公文

*请妥善保存这些链接，因为它们可以作为你后续向面试官阐述“我为什么要做这个项目”的强有力背景证明。*


## 4. 深入剖析招聘启事与技术博客

重点研究两类资料：
1. **招聘需求**：企业期望工程师做什么。
2. **技术博客**：企业内部技术团队实际在攻克什么痛点。

通过分析**招聘启事**，提炼出：
- 核心工作职责
- 必备技能项
- 被反复提及的底层工具链
- 对线上部署和日常运维 (Ops) 的具体要求

通过阅读**技术博客**，找出企业正在解决的问题以及具体实施方案。

**注意寻找以下线索**：
- 他们描述的业务流程/工作流 (workflows)
- 他们面临的技术瓶颈/约束 (constraints)
- 他们踩过的坑与失败模式 (failure modes)
- 他们构建的具体系统架构
- 他们所做的技术折中与妥协 (trade-offs)

随后，可以进一步阅读其技术白皮书和产品文档来摸清业务流细节。


## 5. 提取具体业务痛点

将收集到的笔记整理转化为清晰的**痛点陈述 (Problem Statements)**。

*此时先不要急于构思具体的项目实现方案。*

请用如下格式撰写痛点陈述：
```text
- 客户服务团队需要直接从冗长的政策文档中回答用户的退款疑问，同时绝对不能胡编乱造（幻觉）。
- 金融分析师需要横向比对历年的电话财报会议记录，并自动提炼出随着时间推移而发生改变的风险因素。
- 开发者需要将用户反馈的杂乱无章的 Bug 报告，转化为开发团队可以直接运行复现的 GitHub Issue。
```

每一个痛点陈述应包含：
- **目标用户** (User)
- **输入数据** (Input)
- **输出成果** (Output)
- **失败模式** (Failure mode，即最怕出现什么错误)
- **成功标准/校验方式** (Success check)

如果你无法说清输入数据是什么，或者如何界定系统是否运行成功，那么说明你定义的问题仍过于空泛。


## 6. 设计候选项目创意

围绕痛点列表，构思大约 5 个可行的项目方案。

请使用如下格式设计：
```text
项目名称：退款政策智能客服助手
目标用户：客服专员
输入数据：用户提问 + 企业退款政策说明书
预期输出：基于政策原文回答，引用具体政策条款，并在必要时打上人工介入标签（escalation flag）
求职匹配度：考察 RAG 链路、模型拒答行为、质量评测（Evals）和客服业务场景
```

请尽量保持在同一个行业领域内，但可以设计不同技术维度的候选方案。

以“智能客服”行业为例，你的候选项目可以包含：
- 基于私有知识库的严谨 FAQ 问答助手
- 客服工单自动分类分流工具
- 客户历史通话记录摘要提炼器
- 政策合规自动审查系统
- 客服数据智能分析 Agent

这些是可供挑选的候选项，不是最终都要做的承诺。


## 7. 为每个候选项目做技术选型

在业务痛点被定义清楚之后，再开始做对应的技术方案选择：
- **如果**回答必须要根据特定的参考资料：选择 **RAG（检索增强生成）** 架构。
- **如果**系统需要调用多步工具、维护运行状态或执行复杂动作：选择 **智能体 (Agents)**。
- **如果**用户只需要提取特定字段、标签、分类或摘要信息：选择 **结构化数据输出 (structured output)**。
- **如果**任务根本不需要大模型的概率判断：直接使用 **确定性代码 (deterministic code)**。

你的每一个备选作品，都应当包含能打动面试官的**技术工程信号**：
- 单元与集成测试
- 科学的评测指标与框架 (Evals)
- 系统运行成本与延迟分析
- 日志收集与可观测性监控
- 详细说明设计决策和权衡折中 (trade-offs) 的 README
- 系统 Demo、部署链接、操作演示视频或一行运行的详细命令

请挑选其中具备最佳要素平衡的项目付诸实现：
- 岗位匹配度极高
- 数据源真实可信
- 评测指标清晰明确
- 交付范围在可控时间内
- 具备一定的工程深度
