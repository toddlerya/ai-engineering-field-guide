# 开始项目开发

选定项目之后，在技术灵感冷却或无限膨胀之前，请立即建立代码仓库。

第一步并不是开始写代码，因为你需要首先将早期的调研和筛选工作，沉淀为一份清晰可见的项目计划。


## 1. 初始化项目结构

首先建立一个简单清晰的目录结构：
```text
README.md
PROJECT_PLAN.md
src/
tests/
evals/
data/
.env.example
```
*仅创建你预计会用到的文件夹。*

将样例数据或处理指令放在 `data/` 文件夹中。**切勿**将私有数据、敏感凭证（如 API 秘钥）、抓取条款不明的网页数据或面试涉及的保密资料提交到公共仓库。


## 2. 保存背景佐证资料

将调研出的“业务佐证”写入项目计划中。

记录下：
- 目标行业领域
- 目标对标企业
- 相关招聘启事链接
- 公司技术博客链接
- 产品业务文档
- 收集到的公开数据集或样板文档

请使用具体的超链接，避免使用模糊不清的随手笔记。

**示例如下**：
```text
行业领域：医疗健康 (healthcare)
对标企业：Optum, GE HealthCare, Commure
招聘启事：
- Optum 资深 AI/ML 工程师: https://builtin.com/job/senior-ai-ml-engineer/9555837
企业技术博客及产品源：
- GE HealthCare 研发博客: https://research.gehealthcare.com/blog/
- Commure 技术博客: https://www.commure.com/blog/
```
这能让你的项目具备极强的“抗辩力”（defensibility），因为你可以向面试官清晰地证明该系统诞生的商业合理性与业务背景。


## 3. 编写项目计划书

你可以把计划写在 `PROJECT_PLAN.md`、`docs/project-plan.md`、`README.md` 的开头部分，或者作为 GitHub Issue。

在这一步，你可以合理利用 AI 帮你整理笔记、对比候选方案或起草初版计划。但务必根据你收集到的招聘需求、技术博客、真实数据和技术约束对 AI 生成的结果进行校对。

## 4. 明确定义第一版本（MVP）的边界

清晰地写下第一版本必须达到的指标：
- 能够成功读入小规模数据集。
- 能够通过命令行（CLI）、API 或极其简易的 UI 运行。
- 能产生一个明确有价值的输出。
- 能成功处理一种常见正常业务场景。
- 能妥善处理一种典型的错误失败场景。
- 能通过文档中写的命令顺利运行测试和质量评测。

**同时，明确写下第一版本“不会做什么”**。

**示例**：
```text
第一版本将不会支持多用户注册账号、流式响应（streaming）或自动回写修改原工单。
它目前仅会生成一份草稿回复，供人工进行最终审核。
```


## 5. 选择低门槛的初始技术栈

除非某个前沿框架是你在面试中必须要展示的加分项，否则请选择最普通、最无聊但最稳健的工具。

**推荐的务实技术栈**：
- **Python**：负责后端开发、数据清洗脚本、评测系统以及模型调用。
- **FastAPI / Flask / Streamlit 或直接命令行 CLI**：作为交互界面。
- **SQLite / Postgres 或本地文件**：作为存储介质。
- **向量数据库**：仅当数据检索确实需要时才引入。
- **pytest**：负责确定性的单元测试。
- **轻量级评测脚本**：负责大模型行为与输出质量校验。
- **结构化日志**：记录模型调用、工具调用、Token 费用及响应延迟。
- **README**：附带完备的配置、运行、测试和评测命令。

只有当项目确实需要，或者求职公司有明确要求时，再加入 TypeScript、Docker、CI/CD 流水线或云端部署。


## 6. 从最小闭环开始 (Start Small)

首先开发一条端到端的“最小闭环路径”。

**例如**：
```text
样例输入 -> 数据处理 -> 检索或模型调用 -> 输出格式校验 -> 最终输出
```
开始时不要贪多，不要一开始就去搞精美的监控面板、用户多账号、对接多个模型商或极其复杂的智能体多图编排。

**先让一条核心路径成功跑通，然后再去打磨和扩充它。**
