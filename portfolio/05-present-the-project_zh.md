# 展示你的项目

优秀的仓库能为你争取到面试机会，而清晰的阐述则能帮你锁定最终的 Offer。

请提前做好两方面的准备：
- 一篇高度提炼、易于扫读的项目主页。
- 一个清晰有条理的面试说辞。


## 1. 规范的项目主页

使用 README、作品集独立页面或一份精简的项目案例分析（Case Study）作为展示主页。

页面中应包含：
- 解决的业务痛点
- 目标受众/用户
- 输入数据
- 预期输出
- Demo 展示
- 系统架构
- 测试方法
- 评测指标与结果
- 系统局限性
- 核心代码的入口文件链接

**语言要直奔主题、切忌啰嗦**：

*示例*：
```text
该项目旨在帮助客服专员直接从政策文档中获取信息以解答用户的计费疑问。
系统接收用户反馈的工单内容和一份轻量级的计费政策知识库。
最终返回一份附带原文引用的回复草稿，并在必要时打上人工介入标签。
```


## 2. 核心 Demo 形式

选择一种核心的 Demo 展现形式：
- 线上可访问的 URL 链接
- 短小精炼的屏幕录屏（录像）
- 关键功能截图
- 命令行终端运行录屏 (asciinema 等)
- README 中贴出详尽的输入输出比对样例

*千万不要只寄希望于不稳定的线上 Live Demo。仓库里一定要有截图和样例输出，确保即便线上环境失效，项目依然清晰可读。*


## 3. 60 秒极简自我陈述 (Pitch)

当面试官提出：“请介绍一下你做过的一个项目”时，你可以用这一小段话快速破局。

陈述需要涵盖：
- 业务痛点
- 目标用户
- 解决方案
- 数据成效/佐证
- 个人职责/掌控度

*陈述示例*：
```text
我为中小型 SaaS 团队开发了一个客服工单自动分流与预处理助手。
每当有新工单进入，系统会自动匹配相似的历史工单和计费政策切片，并自动生成一份带引用的分类回复草稿。
我首先完成了项目规划，随后亲自动手开发了 API、检索链路、评测指标以及 CI 测试流。
第一版本在 50 个黄金测试样例中击败了传统关键字检索中的 34 个，但在某些边缘的计费计价场景下仍偶发幻觉。
为此，我补充了拒答逻辑和回归测试集来覆盖这些边缘场景。
```
*在陈述时，请给面试官留下可供后续提问的“钩子”，而不是把所用到的所有开源库名干巴巴地罗列一遍。*


## 4. 技术深度拆解

如果进入到深度的技术讨论环节，请遵循如下顺序进行阐述：

1. 业务痛点与目标用户
2. 输入数据和预期输出
3. MVP 第一版本的边界
4. 整体系统架构
5. 关键技术决策
6. 科学的评测指标与框架 (Evaluation)
7. 测试策略与可观测性监控
8. 演示 Demo 与业务成效
9. 下一步迭代规划

这与标准的 [面试项目深挖环节 (Project Deep Dive)](../interview/questions/03-project-deep-dive.md) 是完全契合的。面试官主要通过这一深挖过程，来考察你的项目所有权、技术判断力以及工程深度。

在讲解完每一个核心段落后，请注意停顿并向面试官确认，将其引导为一场双向互动的技术交流。


## 5. 学会解释技术决策的合理性

准备好解释每一个重要技术选型背后的“为什么”。

**❌ 苍白的回答**：
```text
我使用了向量数据库。
```

**✅ 有说服力的回答**：
```text
我首先以传统的关键字检索作为系统的 Baseline 进行评估。
结果发现，在首批 50 个评测用例中，它遗漏了 11 个表述不同的计费相关提问。
为了解决这一问题，我引入了向量检索，并将关键字检索作为兜底备份（Fallback）逻辑。
```

**可以遵循以下黄金表达模板**：
```text
因为面临约束条件 Z，我最终在 X 和 Y 之间选择了 X。
这种方案的劣势在于 A。
但我之所以可以接受它，是因为 B。
如果后续请求规模扩大，我会对 C 部分进行重构。
```
*你的决策推导过程，远比你最终挑选的底层工具名称更重要。*


## 6. 坦诚探讨系统失败经历

提前准备好一两个关于系统遭遇失败的真实故事。

**适合分享的失败故事包括**：
- 初始版本的提示词经常回答出超出检索上下文之外的内容。
- 文本切片（chunking）策略不合理，导致回答的引用链接断裂。
- 评测集曝光了系统在面对某些敏感输入时未能触发安全拒答。
- 智能体直接调用了 LLM 产生高额费用，而实际上用普通确定性代码即可搞定。
- 现场演示的时延过长，或者请求费用高昂。
- 用户界面上提示正常，但在日志里其实已经疯狂报错。

对于每一个失败案例，请回答以下三个问题：
1. 哪里坏了？
2. 你是如何发现的？
3. 你做了什么调整？

*一个诚实且逻辑清晰的 Bug 解决故事，比一份毫无瑕疵但平淡无奇的技术功能清单更能展示你的工程素养。*


## 7. 深入解释评测方案

随时准备好解答：
- 评测集里包含了哪些类型的用例？
- 评测的标注（Labels）是如何制定的？
- 你拿什么作为对比底线（Baseline）？
- 你挑选了什么核心评估指标？
- 还有哪些边界情况目前系统依然会回答失败？
- 跑完评测后，你对系统做出了哪些具体修改？
- 系统如果部署上线，你需要重点监控哪些核心指标？

即使最终的成效非常微小，也请诚实汇报。

**真实且令人信服的数据支撑**：
- 在评测指标上击败了 Baseline。
- 成功将接口响应延迟或 Token 消耗费用压低了百分之多少。
- 有真实用户测试了 Demo 并给出了反馈。
- 该工具确实自动化地解决了你自身日常工作中的一部分琐碎事务。
- 该项目的评测结果证明：原定的技术方向在当前约束下行不通，应当及时止损。

*“系统目前并不完美，但我能解释为什么” —— 永远好过假装你的 Demo 解决了行业内所有的未解之谜。*


## 8. 清晰申明职责所有权

实事求是地陈述你在项目中扮演的角色。

**清晰的边界划分示例**：
- “我独立起草了项目计划、划定了第一版本的 MVP 范围并构建了评测体系。”
- “虽然这一任务源自公开课程，但项目所在的行业领域、数据集选择、系统架构和测试方案完全由我个人独立构思。”
- “我的队友负责了前端 UI 的开发。我独立开发了后端 API、检索代码和整个评测流。”
- “我使用 AI 编码助手生成了一些样板代码并进行了重构，但是整个核心逻辑设计、测试用例编写，以及评测失败后的架构调整全部由我主导。”

*切勿把教程里的样板工程或团队项目说成是你百分之百的独立个人作品。*
*但也千万不要低估并抹杀你自己在项目中所做出的关键决策和努力。*


## 9. 核心追问准备清单

在每场面试前，重新温习一遍项目计划和 README，并准备好以下问题的简短回答：
- 你当时在解决什么问题？
- 为什么把这几个功能划定为第一版本（MVP）？
- 你在这项工作中的具体职责是什么？
- 系统的哪一部分完全是由你独立设计的？
- 你淘汰了哪些替代方案？
- 你最不满意系统当前做出的哪一项折中妥协？
- 系统跑起来后，最先崩溃的是哪里？
- 你当时是如何调试并定位原因的？
- 你是如何量化评估大模型生成质量的？
- 整个过程中，最让你感到意外的是什么？
- 如果用户量激增，系统哪一部分会最先崩溃？
- 如果重新来过，你会做出什么不同的选择？

*面试结束后，如果发现上述某一个问题回答得不够扎实，请立即更新你的项目计划或 README。*
