# 常见错误规避

失败的求职项目，往往在动笔写代码之前就已经注定失败了。

这类失败作品大多跳过了“痛点摸排”、“质量评测”这两个环节，并且缺乏一份可被他人轻松跑通的项目说明书。


## 1. 技术手段优先（先定技术再套问题）

“我想做一个 RAG 应用” —— 这并不是一个真正的项目主意。

请首先锁定“某人需要完成的一项具体业务工作”。

然后再去挑选适用的技术武器：
- 数据检索 (retrieval)
- 工具调用 (tool use)
- 结构化输出 (structured output)
- 计算机视觉 (vision)
- 数据分类器 (classifier)
- 确定性逻辑代码 (deterministic code)

**RAG 适用场景**：系统回答必须要基于特定参考文档，且不能编造内容。
**智能体 (Agents) 适用场景**：系统需要调用外部工具、根据中间步骤的输出进行自我修正、或者分多步连贯完成任务。
**结构化输出适用场景**：用户仅需要对原始文本提取字段、归纳类别、生成特定格式摘要或决定响应动作。

Reddit 和 X 上围绕 AI 工程师作品集的讨论一再发出相同的警告：**没有评测（Evals）、没有日志（Logs）、没有对比基准（Baselines）且没有定义明确业务问题的 generic chatbot/RAG demo，在求职时没有任何竞争力**。详细可参考 [讨论笔记](_internal/discussion-threads.md)。


## 2. 盲目挑选对标公司

挑选对标的求职企业时，不要仅仅冲着名气去。

应当先挑准你想投递的目标岗位，然后将它们归类到具体的行业领域中：
- 智能客服 (support)
- 电子商务 (e-commerce)
- 法律与合规 (legal)
- 医疗健康 (healthcare)
- 金融领域 (finance)
- 开发者工具 (developer tools)
- 在线教育 (education)
- 物流供应链 (logistics)

如果你的项目一会儿针对 OpenAI，一会儿针对 Stripe，一会儿又针对某家三甲医院，那在面试中阐述时就会显得缺乏专注度。

但如果你的项目定位非常精准：*“开发一个辅助 B2B 客服团队从长篇幅政策中检索退款依据的工具”* —— 那么系统的目标受众、数据输入、预期输出以及质量评测集（Eval cases）都会非常清晰聚焦。


## 3. 被动地阅读技术博客

技术博客只有当你能从中提炼出真实的“业务痛点”时才有用。

阅读博客时，请带着这些问题思考：
- 技术团队试图提升或优化的具体工作是什么？
- 业务人员原本需要手工阅读、决策、派发、归纳或审核什么内容？
- 牵涉到哪些数据源？
- 为什么老旧的流程会导致工作变慢、变贵、面临合规风险或质量参差不齐？
- 这是一个什么样的场景？如果做一个简化版但有用的 MVP（最小可行性版本）应该长什么样？
- 如何科学评测这个系统到底有没有发挥效果？

**被动的学习只能让你收集一堆时髦的黑话词汇，主动的解剖才能帮你提炼出产品技术指标。**


## 4. 无法清晰描述核心痛点

一个行业领域本身，并不能等同于一个具体的痛点。

**❌ 过于宽泛的描述**：
```text
医疗健康 AI
```

**✅ 具体的描述**：
```text
将医患问诊记录自动归纳提炼为结构化的随访指导信息，并在面对患者提出医疗处方建议时触发安全拒答路径。
```

在开始写代码前，务必写清楚：
- 谁是目标用户
- 他们提供什么数据输入
- 他们需要什么格式的输出
- 第一版本（MVP）的边界在哪
- 你如何校验系统质量

如果你无法给出明确答案，请退回到调研阶段重新摸排。


## 5. 开发同质化的通用聊天机器人 (Generic Chatbot)

“上传 PDF 然后和它聊天” 已经过于同质化，很难打动面试官。

**更有说服力的设计应该指出明确的用户与任务**：
- 客服主管对照公司政策审核用户的退款工单。
- 法务分析师从供应商合同中提取高风险的霸王条款。
- 开发者关系团队将 GitHub Issue 自动转化为分类评级好的内部工单。
- 电商平台卖家利用商品图片和粗糙的手记自动生成精美的商品详情页描述。

“聊天框”可以作为最终呈现的前端交互界面，但绝对不应是项目核心创意的全部。


## 6. 滥用并不适配的复杂工具

盲目追求 RAG、Agent 和多智能体（Multi-agent）架构会大大增加开发与运维成本。

它们会带来：
- 复杂的数据清洗和灌入
- 工具 Schema 编写与维护
- 各种接口报错处理
- 分布式链路追踪（Traces）
- 复杂的評测集设计
- 各种奇奇怪怪的失败边界

**只在业务痛点确实需要时，才引入高级的技术方案**：
- 如果只是要提取文本字段：直接使用**结构化输出（Structured Output）**。
- 如果回答需要指出经常变动的文档出处：使用 **RAG 架构**。
- 如果需要查询外部 API 或写库更新状态：使用 **工具调用（Tool Calling）**。
- 只有当不同的角色分工能让评测（Evaluation）变得更简单时：才考虑引入 **多智能体架构**。

如果调用单次大模型 API 配合简单的确定性业务逻辑代码就能解决第一版本的问题，那就从最简单的地方开始。


## 7. 缺乏科学的评估方案 (Evaluation)

AI 项目需要提供一种量化的方式，来判定每一次代码或提示词的改动是否真的改善了系统表现。

请从编写 **20-50 个** 评测用例开始：
- 简单场景
- 复杂数据场景
- 超出业务边界的请求
- 安全拒答场景
- 需要提供出处引用的检索用例

**挑选适配业务的评测指标**：
- **RAG**：评估回答相关度和引用准确度。
- **信息抽取**：评估字段准确率和数据 Schema 校验。
- **智能体**：评估工具调用准确率和任务执行成功率。
- **多步长系统**：评估响应时延、Token 消耗和调用成本。
- **安全敏感任务**：评估安全拒答率。

面试官和作业评审人员在 [Take-Home 面试作业](../interview/questions/06-home-assignments.md) 中，高度关注候选人是否有清晰的评估逻辑。


## 8. 没有可观测性监控规划

可观测性监控可以从最基础的本地文件日志做起。

记录关键的字段：
- 请求 Request ID
- 调用的模型型号
- 提示词版本号
- 检索到的原始分块
- 调用的工具和入参
- 格式校验报错
- 时延
- Token 消耗
- 运行成本
- 用户反馈/点赞点踩

这些运行日志能帮你调试 Bug，更能证明你是在像设计传统软件系统一样，严谨地对待和治理 AI 系统。


## 9. 杂乱无章的代码仓库

即使系统跑得再好，如果代码仓库杂乱无章、缺乏基本的阅读指南，在求职时依然会大打折扣。

请规范好你的代码库：
- **`README.md`**：解释痛点、受众、MVP 版本边界、Demo 展示和设计妥协（trade-offs）。
- **`src/` 或应用目录**：存放核心生产业务代码。
- **`tests/`**：存放确定性逻辑的单元测试。
- **`evals/`**：存放评测数据、评测引擎和评测记录。
- **`data/`**：存放样例数据或处理说明。
- **`.env.example`**：存放本地环境配置模板。
- 最好能配置自动化的 CI，在 Push 代码时自动跑一遍测试和评测。

无论是公开的作品集还是面试作业，核心考察的始终是这些软件工程基本功：
- 结构清晰的 README
- 完备的环境配置与运行命令
- 单元与集成测试
- 科学的评测指标
- 对设计妥协和权衡决策的清晰解释

具体可参考 [本地语料库](_internal/local-corpus.md) 和 [讨论笔记](_internal/discussion-threads.md)。


## 10. 构思项目时的自查清单

在敲定你的项目点子前，请先自问：
- [ ] 我能明确说出这个项目的目标领域和受众是谁吗？
- [ ] 我参考了真实的对标企业或真实的业务流程了吗？
- [ ] 我提取出了具体的痛点陈述吗？
- [ ] 我有贴近真实业务的输入数据吗？
- [ ] 我选择的技术手段能严密对齐目标任务吗？
- [ ] 我能给第一版本（MVP）划定清晰的边界吗？
- [ ] 我有明确的质量评测（Evaluation）方案吗？
- [ ] 我有收集失败记录、响应延迟和 Token 成本的日志方案吗？
- [ ] 我能让整个代码库变得极易被他人跑通并进行讨论吗？

如果有任何一项自查没通过，说明你的项目方案还没准备好，请暂缓动笔开发。
