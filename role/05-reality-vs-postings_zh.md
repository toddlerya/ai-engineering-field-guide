## AI 工程师 vs 机器学习工程师 (MLE)：职位混淆

* **痛点**：头衔与职责错位。招聘人员在岗位标题写着“AI 工程师”，实际想招的却是“机器学习工程师”，反之亦然。
* **数据来源**：
  - Reddit 讨论：[AI Engineer Vs ML Engineer, what's the difference?](https://www.reddit.com/r/learnmachinelearning/comments/1nu6ug7/ai_engineer_vs_ml_engineer_whats_the_difference/) - r/learnmachinelearning

**业界讨论达成的共识**：
- **ML 工程师**聚焦于模型的训练与权重调优 (training/tuning)。
- **AI 工程师**侧重于把现成的预训练模型集成到上层业务应用里。
- “AI 工程师”头衔在很大程度上是生成式 AI (GenAI) 爆发后，对岗位进行的一次重新包装。

### 候选人汇报的真实尴尬

- 申请了 AI 工程师岗 $\rightarrow$ 面试时却被狂问传统机器学习推导（如 SVM、随机森林）。
- 满心期待去开发智能体工作流 $\rightarrow$ 入职后被要求从零开始训练定制化的基础模型。
- 想做大模型 API 集成开发 $\rightarrow$ 结果在面试环节被狂拷底层 GPU 调度和基础设施网络。


## AI 工程师具体在做什么

### 三种主要工作类型

#### 1. 编排型 (Orchestrators) —— 约占 50%
负责 RAG 数据流、向量数据库与智能体工作流。
* **典型工作内容**：
  - 构建“ATOM”：具有长期记忆整理能力的本地智能助手。
  - Slack 历史对话智能问答：解析历史讨论帖子，解决长上下文衰减问题。
  - 线框图一键转代码 UI 智能体：将设计图转化为可用代码。
  - 多租户后端开发：为每个用户隔离向量数据库命名空间，实施 Token 预算控制。
  - 智能体博弈系统：设计能互相调整对方运行参数的 Agent 对抗体系。

#### 2. 评估型 (Evals Specialists) —— 约占 40%
负责开发模型评估框架。
* **典型工作内容**：
  - 构建“大模型作为裁判 (LLM-as-judge)”系统：利用高阶模型对其它模型的输出进行打分。
  - 黄金测试集建设：设计精心维护的测试用例集，以衡量 RAG 的召回与准确表现。
  - 幻觉拦截检测：追踪生成式回复何时偏离了检索到的事实上下文。
  - 生产性能统计：追踪 Recall@K、单次查询时延、每千次请求的成本波动。

#### 3. 效率包装型 (Efficiency Wrappers) —— 约占 10%
负责流式传输、提示词缓存与投机采样解码。
* **典型工作内容**：
  - 语义缓存 (Semantic caching)：对高度相似的问答请求直接返回缓存结果。
  - Token 消耗优化：设计特定领域的 Tokenizer 从而降低输入序列长度。
  - API 频率超限 (Rate Limit) 处理：在多个大模型服务商之间做热备降级和轮询分发。
  - 智能模型路由：简单任务用低价模型，高精任务路由到昂贵模型。

### 实际日常工作 vs 主观臆断

* **“整天就是写提示词”** $\rightarrow$ **现实**：编写用于根据上下文动态生成和编排提示词的程序逻辑。
* **“调用 OpenAI 的 API 就行了”** $\rightarrow$ **现实**：构建多模型备用方案、可观测性监控、成本分账系统。
* **“做模型训练”** $\rightarrow$ **现实**：极少。主要是直接调用商业 API，或本地加载开源模型权重做应用。
* **“在 Jupyter Notebook 里写代码”** $\rightarrow$ **现实**：快速移步到基于 FastAPI/Go 编写的生产级 API，配合 Docker 进行 CI/CD 自动部署。

### 真实的调试循环 (The Debug Loop)

开发者在日常调试中反映的真正痛点：
- 为什么 LLM 在执行包含了 50 个步骤的 Agent 长链条任务时，突然遗忘了第 12 步的约束？
- 向量检索召回的哪一个分块 (chunk) 诱导了模型给出幻觉回复？
- 怎么在不降低输出质量的前提下，最大程度压低 Token 的消耗？
- 当多个大模型 API 服务商同时出现限流或访问超时，系统如何实现无缝的主备切换？


## 招聘描述与实际体验的差距

| 维度维度 | 招聘启事里怎么写 | 工程师入职后怎么看 |
|-----------|------------------|---------------------------|
| **RAG** | 核心技能（35.9% 提及） | 已变成默认基准线 —— 现在如何做自动化评估 (Evaluation) 更加吃香 |
| **微调 (Fine-tuning)** | 经常被高调提及 | 极少被直接考查，除非是极其垂直的算法团队 |
| **机器学习知识** | 64% 的岗位要求懂点 ML | 实际工作中，ML 理论要求往往低于全栈工程交付能力 |
| **全栈技能** | 93% 的岗位要求 GenAI 之外的技能 | **确实如此** —— 普遍要求候选人能独立负责端到端功能交付 |
| **AI 辅助开发工具** | 基本不提 | 实际开发高度依赖，但在某些公司的手撕代码面试中却被严厉禁用 |


## “全能岗位 (Combo Role)” 带来的困境

* **吐槽最集中的点**：企业期望候选人“一专多能”，一个人干三个人的活。
* **现实情况**：很多公司招聘的“AI 工程师”实际上是一个糅合了以下职能的混合体：
  - **机器学习工程师**（训练和调优模型）
  - **MLOps 工程师**（管理算力和部署基础设施）
  - **数据工程师**（清洗和准备训练集流水线）
  - 以及**真正的 AI 应用工程师**（大模型应用编排）


## 核心启示

1. **职位头衔依然存在混乱**：“AI 工程师”在不同公司代表的工作内容可能大相径庭，求职时务必看清具体职责描述。
2. **生产思维决定胜负**：相比于追求极端的回答准确率，企业在生产环境中更看重成本控制、响应延迟和系统可观测性。
3. **评估能力才是核心壁垒**：构建大模型应用门槛很低，但能用科学的测试指标度量应用质量并持续优化的人凤毛麟角。
4. **端到端交付的系统负责人最受欢迎**：能够打通“构建 $\rightarrow$ 部署 $\rightarrow$ 扩容 $\rightarrow$ 度量”全流程的复合型人才备受青睐。
5. **面试与工作的断层**：招聘要求写的内容，往往和面试中拷问的知识，以及入职后实际从事的工作有较大的断层。
