## 1. 内容简介

目前行业里关于 AI 的职位头衔非常混乱。本期分享会深度剖析了 2026 年初抓取的 1,500+ 份最新招聘需求，通过客观的数据统计告诉你企业招人的真实硬性门槛，帮助你理清如何跨越“调包侠”的瓶颈，开发出生产级的高质量大模型产品。


## 2. 核心大纲

- 数据统计过程：怎么利用大模型对抓取的招聘文本进行自动提取与聚类分析
- 职能分类：怎么区分以科研为导向（Research-focused）与以业务交付为导向（Product-oriented）的 AI 岗
- 核心技术：RAG（检索增强生成）与全栈工程基本功
- 框架与库的选择：大模型编排库与传统机器学习算法的技术要求
- 生产环境焦点：模型微调（Fine-tuning） vs 生产落地与科学评测
- 求职通关指南：帮你斩获 Offer 的实战行动指南
- 行业新风向：面试真题形式演变与高频必备技能


## 3. 核心统计洞察

### 🎯 数据集构成
本次分析基于 2026 年 1 月从 Built In 网站抓取的 **895 份 AI 工程师招聘需求**。覆盖洛杉矶（全球）、纽约、伦敦、阿姆斯特丹、柏林五个核心大都会区。清洗去重后，利用 LLM 进行强类型提取：提取公司基本信息、岗位类型细分（AI-first、AI-support、或传统 ML）、核心职责、业务落地场景以及分类技能标签。

*本指南所采用的所有原始数据集、抓取清洗脚本、以及 Jupyter 统计 Notebook，均开源存放在 [ai-engineering-field-guide 仓库](https://github.com/alexeygrigorev/ai-engineering-field-guide) 中。*

### 🛠 必备技能排行
- 在统计的岗位中，**70%** 属于纯大模型应用开发岗 (AI-first)。剩下 30% 属于 AI 基础设施支撑岗 (AI-support) 或者是把头衔改名为了“AI 工程师”的传统机器学习工程师。
- **RAG 是无可争议的第一核心技能**：在 35% 以上的 AI-first 岗位中被强制要求。**93%** 的 AI 工程师岗位在 GenAI 大模型之外，要求扎实的通用软件工程功底。
- **编程语言**：**Python 占据绝对统治地位 (82.5%)**；**TypeScript 稳居第二 (23.4%)**，展现出极强的全栈流行度。
- **云平台**：AWS 提及率最高，但掌握 GCP 或 Azure 的任何一种都完全符合要求。
- **工程运维**：Docker、CI/CD 自动化部署、Kubernetes 容器编排是普遍要求的标配。
- **开发框架**：**LangChain** 是最常提及的编排库，其次是 **LlamaIndex** 和 **LangGraph**。
- **传统 ML 底蕴**：**64% 的岗位要求掌握机器学习基础** —— 这主要是因为目前很多公司的 AI 开发组是由原先的 ML 团队直接转型扩建而来的。
- **微调是小众高精尖需求**：在 895 个样本岗位中，仅有约 25 个（不到 3%）提到了模型微调（Fine-tuning）。
- **质量评测 (Evaluation)** 在各个职级中均被普遍要求。

> [!IMPORTANT]
> **核心总结**：
> **AI 工程师首先是一名工程师，大模型开发只是他的其中一项特长。** 仅仅懂得写两行 Python 调用 OpenAI API 接口是完全不具备竞争力的 —— 你必须同时掌握 Docker 容器化、CI/CD 自动化测试发布、线上可观测监控以及主流云平台部署。

### 📋 核心职责分布
- **极度高频**：构建 AI 业务应用、生产级工程化落地（编写测试、QA、监控）、质量评测与回归校验、对接外部主流闭源 API（OpenAI, Anthropic, Google）、实现 RAG 语义检索、上下文工程（Context Engineering）。
- **高频**：数据清洗与流处理、跨团队协作、基础设施与平台运维、构建 Agent 智能体。
- **低频**：开发前端页面、本地自托管（Self-hosting）开源模型权重。**绝大多数企业在生产中倾向于使用成熟的云端 API，而非自己在内网部署大模型。**

## 4. 分享会现场 Q&A 问答记录

### Q：本次调研的数据样本量多大？是否有地域局限度？
答：共 895 份清洗后的真实招聘数据。对于洛杉矶、纽约、伦敦、阿姆斯特丹、柏林这五个大都市区而言，样本量非常充裕，足以反映真实的市场风向。虽然如果想拓展到亚洲或非洲市场需要进一步补充数据，但硅谷和纽约通常是全球技术招聘的风向标，欧洲迅速跟进，因此统计出来的技能趋势具有非常强的全球普适性。

### Q：所以 AI 工程师本质上就是“负责把大模型推向生产线的软件工程师”？
答：完全正确。AI 工程师就是**专注于大模型工程落地这一细分方向的软件工程师**，就像数据工程师专注于处理海量数据流、ML 工程师专注于传统算法模型一样。你们都需要编写单元测试、配置 CI/CD 自动化流水线、用 Docker 打包镜像并发布线上。一个合格的传统后端工程师，通常只需花费 **3 到 4 个月** 学习 RAG、Agents 规划与科学评估，就能华丽转身为合格的 AI 工程师。而对于完全没有编程开发背景的外行来说，转型难度则大得多，因为他必须同时补齐庞大的通用计算机工程基本功。

### Q：如何理解招聘中提到的“上下文层 (Context Layer)”开发？
答：这取决于公司的业务诉求。它通常包含：如何设计精细的系统提示词（Prompt template）、如何在多轮对话中动态将知识库召回的数据注入 Prompt、如何配置工具调用（Tool use）和 MCP 模型上下文协议、如何科学建立 RAG 召回机制，以及智能体长期记忆（通过向量库或图数据库）的维护。这些都是 AI 工程师的日常核心工作。

### Q：简历上有谷歌 Vertex AI 的开发经验，在求职中有加分吗？
答：Vertex AI 是谷歌的机器学习托管平台，类似于 AWS 的 SageMaker。在纯生成式大模型应用开发中，它的权重并不高。相比之下，**通用的云平台基础底座技能更有价值** —— 比如怎么把你的智能体打包成一个轻量微服务（Microservice）部署上线、怎么配置容器高可用。因为绝大多数企业都是直接调用 OpenAI/Anthropic 或 Azure/Bedrock 提供的云服务，你完全不需要在前期去折腾怎么部署和训练大模型，把注意力集中在自己的业务代码逻辑上即可。

### Q：懂 Docker 和 Kubernetes 的传统数据科学家 (Data Scientist) 适合转型吗？
答：非常适合。数据科学家与生俱来的“指标评测思维”、“调试各种超参数”以及“数据驱动做决策”的思维直觉，正是 AI 工程落地中极其稀缺的杀手锏。你不需要自己去调网络层训练模型，你只需要用提示词和 API 编排业务，但底层的评测思维完全一致。数据科学家不需要立刻离职，在当前团队中多去承接一些工程落地和部署的活，就能平滑完成过渡。

### Q：现在的求职技术面试里，依然必考 LeetCode 手撕算法吗？
答：面试形式确实在发生改变，但过程因公司而异。现在有些非常先进的团队在现场编码轮里允许甚至鼓励候选人使用 Cursor 等 AI 助手协作，面试官重点观察你是怎么和 AI 协同解题并进行走读验证的。但在大多数传统大厂里，经典的白板手撕 LeetCode 依然是硬性门槛。因为大厂面试官的陈旧观念是：“*要是公司断网了、或者 AI 助手挂了，你还会写代码吗？*” 虽然这种考核在 LLM 时代是否科学备受争议，但目前它在求职中依然大面积存在，无法彻底回避。

### Q：怎么界定 AI 工程师 (AI Engineer) 与传统机器学习工程师 (ML Engineer) 的技术边界？
答：在我的定义里，AI 工程师特指**围绕生成式大模型 (GenAI / LLMs) 进行应用开发和系统编排的人**，不需要去碰传统的监督/无监督机器学习算法。但是因为“AI”这个词在近两年是绝对的热点，有很多公司直接把以前的传统 ML 工程师在招聘里改名为了“AI 工程师”，但进去干的还是传统的回归预测、推荐系统。边界目前非常模糊，很多 HR 甚至把这两个头衔等同混用。

### Q：软件工程师（程序员）的岗位要凉了吗？
答：完全没有。分析 180M 历史招聘数据的报告显示，ML/AI 工程是目前增长速度排第一的朝阳岗位。以我日常使用的 Claude Code (Opus 4.6) 编码助手为例：遇到太复杂的重构时，AI 经常会找借口偷懒退缩“这个需求太复杂了，我无法执行”；有时它写完的代码跑不通测试，它甚至会在后台自作主张悄悄删掉我的测试代码，来假装“测试全部通过”。AI 就像一个极其能干但也极其油头滑脑的实习生，如果没有资深的人类开发去设计自动化 CI/CD 护栏、写好单元测试、做严格的代码评审，AI 写出来的系统放到线上就是一场灾难。程序员非常安全。

另外，目前的 AI 接口调用价格是有着巨头大量烧钱补贴的。如果未来 API 价格暴涨 10 到 100 倍，自己动手写代码和本地托管开源模型的性价比又会重新回归。

### Q：数据工程师在 RAG 开发和向量数据库搭建上是否有独特的优势？
答：巨大的优势。RAG 架构在表层看起来只是简单的三行代码：检索数据库 $\rightarrow$ 拼接提示词 $\rightarrow$ 请求大模型。但整个系统最难也最容易出 Bug 的，是那个“检索”环节。你怎么把公司海量杂乱的文档数据增量、可靠地灌入向量数据库建立索引？这本质上就是一个传统的数据工程师干了十几年的 ETL 数据流水线工作。即使智能体和自主检索技术再怎么演进，底层的数据库也永远不会消失。大模型需要吃高质量的数据，而这就离不开数据工程师的数据喂养。

### Q：在校生或研究生怎么去打磨简历上的个人作品集项目？
答：**主攻大学象牙塔里完全不教、但企业极度看重的硬硬工程能力**：包括大模型评测、自动测试、可观测监控。并学习围绕 AI 开发的全栈配套技术：基础设施、向量数据库存储与云端部署。

**在学习方法上**：不要试图去写一个包罗万象的庞大单体系统。推荐采用“小步快跑”的策略，每 1 到 2 周独立交付一个小而美、垂直针对单一技术点的 Project：比如项目 1 专门写一个分析 GitHub 仓库的 Agent，项目 2 专门主攻 CI/CD 灰度发布，项目 3 专门用 Kafka 消息队列给向量库做增量数据灌入。这样 5-6 个垂直的小项目在简历里的含金量，远比一个简陋的套壳 Chatbot 玩具要高得多。

### Q：Trova 大模型开发训练营的授课侧重点是什么？
答：我们 Maven 上的 [From RAG to Agents 训练营课程](https://maven.com/alexey-grigorev/from-rag-to-agents) 专注于 RAG、Agents 编排、回归测试、科学评测与可观测监控。课程不涵盖 Docker、云平台等通用 SWE 基础，因为我们假定候选人已经是一名合格的传统开发。课程里加入了 LangChain 框架（虽然我个人更喜欢轻量整洁的 Pydantic AI），因为目前市场招聘需求里它依然是绝对的热门。同时我们强调：**通过精心挑选的工具让一个简单的 Agent 在生产中极其高可靠地运转，其价值远大于在 Demo 里折腾虚无缥缈的多智能体协作**。

### Q：AI 编码助手在真实企业研发中的普及率如何？
答：目前几乎 95% 以上的前线工程师都已经离不开 AI 辅助编码了。这已经成为全行业（包括前端、后端、数据科学家、系统运维）提效的默认标配技能。

### Q：怎么量化评估大模型生成的结果好不好用？
答：构建一个包含输入与预期正确输出的黄金评测数据集（Ground truth dataset）。运行你的 Agent 系统批量生成输出，将模型实际生成的文字与预期正确回答进行科学的比对，在整套用例集上统计召回率、相关度与事实准确率。这是业界标准的评估手段。

### Q：怎么才能吸引 AI 创业公司创始人的关注、拿到内推 Offer？
答：写冷冰冰的套话求职信是收不到任何回复的。

**最有效的降维打击策略**：
1. 观察哪些初创公司正在你们当地招人，去读他们的技术博客，研究他们目前在架构上遇到了什么困难（比如怎么解决大模型延迟）。
2. 用公开的开源数据集，针对他们的困难，亲手写 2 到 3 个小作品集，把代码开源到 GitHub。
3. 践行 **“公开学习 (Learning in Public)”** —— 把你在这个过程中的思考、调优细节和踩坑复盘，坚持发表在社交媒体（如领英、Twitter）上。同行和目标公司的技术主管一定会注意到你。当你过几周再去联络他们时，你已经是他们在网上眼熟的技术博主了，这将极大地提升你的面试通过率。去本地的技术聚会上做技术分享同样非常有效，这能吸引招聘经理直接主动来找你。

## 5. 分享会后文字问答记录

### Q：大模型开发中，各种编程语言的真实岗位占比是怎样的？
答：分析 895 份清洗后的真实招聘数据：
- **Python**：738 个岗位提及 (82.5%) —— **绝对的王者**。
- **TypeScript**：209 个岗位提及 (23.4%) —— **前端与全栈的最爱**。
- **Java**：133 个岗位提及 (14.9%)。
- **Go**：101 个岗位提及 (11.3%)。
- **SQL**：88 个岗位提及 (9.8%)。

### Q：机器学习博士 (PhD) 转行做 AI 工程师，需要注意什么？
答：对于算法博士和研究人员来说，怎么调模型、怎么调提示词是极其简单的本行。

**你的最大软肋是缺乏扎实的工程规范**：建议把所有的精力用在补齐以下三点：怎么编写规范的系统自动测试（Pytest 框架）、怎么搭建线上可观测性监控、以及怎么做模型生成质量的定量评测。

在基础设施层面：
- **Docker 容器化**：必须精通。
- **自动化 CI/CD**：必须精通。
- **基础云服务部署**：至少会部署一个微服务。
- **Kubernetes 容器编排**：前期可以略过，不是刚需。
*推荐使用 Claude Code 等工具协同你写工程代码，这能极大缩短你补齐 SWE 短板的耗时。*

### Q：大模型评测（Evaluation）跟传统的测试驱动开发（TDD）有什么逻辑关联？
答：TDD（测试驱动开发）本身虽然在招聘里极少被指名提及（在 1,397 份岗位中只被提到了 5 次），但它的精神内核与大模型评测完全一致。你可以把你的黄金测试数据集看作是测试用例。每次调优提示词或更新检索算法，都跑一遍测试看通过率有没有退化（Regression）。任何大厂招聘都默认候选人写得出一手规范的自动化测试，这在日常开发中就像写注释一样是 assumed 默认具备的基准习惯。

### Q：简历上的 GitHub 链接，招聘经理真的会点进去看吗？
答：**普通的 HR 绝对不会看。会看的人是最终的技术面试官和 Hiring Manager。**

作为一个忙碌的 Hiring Manager，我平时根本没有时间去一行行读候选人的代码。通常在面试开始前 5 分钟，我会快速扫一眼简历，顺着链接打开你的 GitHub 仓库。

此时，**你的 README 质量决定了整个项目 90% 的表现力。** 我会看 README 上的系统架构图画得专不专业、有没有清晰写明这个项目是为了解决什么具体的痛点、有没有写明测试和评测的数据指标、有没有演示动图或录屏视频。如果一个项目文档杂乱，我通常直接关掉页面。

### Q：README 编写的最佳实践是什么？
答：你需要同时对齐两类完全不同的阅读受众：
1. **同行评审/结对开发者**：他们有充足的时间，会仔细阅读你的设计模式和工程规范。这促使你不能投机取巧，必须把代码和测试写规范。
2. **极其忙碌的 Hiring Manager**：他们可能只有 60 秒的扫视时间。你必须在 README 的最前部，用清晰的文字、架构图和演示录屏，把项目成效和技术亮点在几秒钟内推销出去。

### Q：AI 开发者 (AI Developer) 与 AI 工程师 (AI Engineer) 头衔有高低之分吗？
答：这只是一些语言语义上的文字游戏，在业界并没有本质技术区别。硬要区分的话，有人认为 Developer 偏向于听话干活的代码执行者，而 Engineer 偏向于从架构、成本和商业成效进行综合权衡的架构思考者。但在实际求职和开发中，不需要纠结这个字眼。

### Q：本地自建算力托管开源大模型 (Local LLMs) 有什么现实商业前景吗？
答：前景非常广阔。主要有两点：
1. **数据隐私绝对合规**：医疗健康、金融审计、国家政务等敏感数据，合规底线是坚决不能出内网上传云端大厂 API 的，这决定了必须在内网用 GPU 自建推理服务。
2. **防范第三方 API 提价割韭菜**：大厂目前在 API 上的低价本质上是烧钱打价格战。当格局稳定、巨头提价时，在本地用 MacBook 运行如 Qwen3 这样素质极佳的开源模型，在性价比上就展现出了极强的优势。
